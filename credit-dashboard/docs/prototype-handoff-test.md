# API契約から作成した試作フロントエンド

作成日: 2026-10-28。

## 目的と確認の境界

引き継ぎ文書とHTTP APIだけで別のフロントエンドを作り、バックエンドの実装を参照する必要があるか確認する。既存画面は保持し、試作版を`http://localhost:8000/prototype/`へ追加した。

今回の実装では次を参照した。

- `AGENTS.md`
- `docs/handoff.md`
- `docs/data-contract.md`
- `docs/timetable-csv.md`
- `docs/recommendation-api.md`
- `docs/recommendation-search-api.md`
- `examples/README.md`
- 上記仕様のlocalhost HTTP APIに対する、架空CSVだけを使った応答

今回の作成・検証ではPythonのバックエンドソース、規則JSON、カタログの内部JSON、既存の画面用JavaScriptを読まず、バックエンドモジュールもimportしていない。過去の会話にはバックエンドを参照した履歴があるため、前知識のない第三者による完全な独立検証ではない。今回の実装に必要な追加情報を、文書または公開APIから取得できるかという検証である。

## 実装

| ファイル | 責務 |
| --- | --- |
| `static/prototype/index.html` | 単位の状況・時間割と教養・科目一覧の画面 |
| `static/prototype/styles.css` | デスクトップ・タブレット・スマートフォンのレイアウト |
| `static/prototype/api.js` | 文書のURL・multipart項目・JSON版に基づく独立した通信クライアント |
| `static/prototype/app.js` | 元File・公開プロファイル・API結果のメモリ管理と表示 |
| `scripts/check_prototype.cjs` | HTTP APIと実ブラウザーだけを使う自動確認 |

追加フレームワーク・外部CDN・外部フォントは使用しない。JavaScriptの標準モジュールとCSSで構成し、既存UIの`window.creditWorkspace`や`window.createRecommendationClient`には依存しない。これは試作版の実装選択であり、別担当がReact等を採用することを制限しない。

成績CSVは選択・ドロップ時に解析し、修得済み単位、教養・専門の内訳、学年別の要件、個別必修を表示する。要件カードには総合判定と進捗を表示し、条件の内訳はすべて初期状態で折りたたむ。条件は展開後の一覧に1回だけ表示し、「不足・要確認だけ」で絞り込んだ場合も同じ開閉方法を使う。公式根拠も展開して確認する。科目一覧は検索・区分・修得状況で絞り込み、25件ずつ表示する。行数に上限を設けずページを切り替えられる。

画面には「試作」などの開発用ラベルや従来画面への導線を置かない。APIが返す注意事項のMVPに関する表現は、表示時だけ利用者向けの文へ置き換える。対象範囲、公式規則との差、ターム0を除外した科目との時間重複未確認、判定不能の理由は残す。APIのコード・状態・数値や学務判定は変更しない。

教養候補の所属は単位集計側の選択を共有する。履修表のある場合はAPIが返す年度・タームを使用し、ない場合は対応カタログの最新年度を明示する。時限の候補閲覧と不足単位の探索を別操作とし、取得済み・要確認・未修得を混同しない。

APIの総合判定・条件別判定をそのまま表示する。進捗バーは同一条件の必要値と確認済み値、または条件の充足項目数の表示だけに使う。単位配賦・学務判定・推薦効果の計算は行わない。

## 文書だけでは不足していた情報

バックエンドのソースを読む必要はなかったが、当初の仕様書だけでは次の情報が不足した。APIを架空データで呼び出して確認し、`docs/data-contract.md`へ補足した。

| 不足していた項目 | 取得方法・補足 |
| --- | --- |
| 規則一覧のエンベロープ | `profiles`・`default_profile_id`、要件メタデータの形をGET応答で確認し、JSON例を追加 |
| `summary`の詳細 | 既存文書は`{}`で省略されていた。集計値・`majors`・`categories`のキーと意味を補足 |
| 科目の`status` | 仕様の`result`と同じ正規化状態が返ることを確認。`source_result`との区別を補足 |
| 条件の種類別の数値 | 単位・在学期間・個別必修で項目が異なるため、表示に必要な項目と判定不能時の説明を整理 |

条件ID・必要単位数・対象年度を画面へ固定せず、API結果を使った。`schema_version`だけでは全項目の型検証はできないため、OpenAPIまたはJSON Schema・フロント側の型を揃える課題は残る。

## 実行方法

クローン後、`compose.yaml`のあるプロジェクト直下で次を実行する。起動用カタログと架空CSVはGitに含まれるため、ZIPの配置は不要である。

```bash
docker compose up --build -d
```

試作版は`http://localhost:8000/prototype/`、従来版は`http://localhost:8000/`。試作版を別ホストで配信する場合は、既存の契約どおり`/api`をプロキシするか、通信クライアントのベースURLとバックエンドの明示的CORSを設定する。

実ブラウザーの確認にはPlaywrightとChromeまたはChromiumが必要で、アプリケーションの実行依存には追加していない。

```bash
node scripts/check_prototype.cjs --examples-dir examples
```

`--base-url`でlocalhostの別ポート、`--screenshot-dir`で架空データの画像の出力先を指定できる。CSV・API応答・動画・トレースは保存しない。実在する学生データは使わない。

## 確認結果

確認結果は`docs/testing.md`の試作フロントエンド節へ記録する。検証対象は表示・操作・API連携であり、大学の学務規則の正しさを再監査したものではない。

同日の表示修正後は全33項目が成功した。閉じた状態での条件非表示、展開時の重複防止、絞り込み後の開閉、開発用文言の非表示と必要な注意事項の保持を追加確認した。
