# 教養科目の履修推薦：設計メモ

2026-10-26からの利用者指定の要件と、2026-10-27時点の実装を記録する。履修表の読み取り、タブ切替の参考UI、Gコードカタログ生成、指定枠の候補検索、修得単位と空き時間を照合する教養探索をAPI・画面から利用できる。順位付けと複数候補の履修計画は未実装である。

## 1. 確定した範囲

- 最初の対象は新潟大学工学部・知能情報システムプログラム・2025年度入学の既存MVPとする。
- 推薦は教養科目だけ。専門科目を教養へ回す既存の集計方針と、推薦候補の対象範囲は別に扱う。
- 不足単位の探索では教養の必修・選択必修・選択・合計がすべて充足したら推薦を止める。専門と共用する超過分や総計の不足だけでは教養を推薦しない。未充足の教養条件を改善する候補だけを選ぶ。
- 2026-10-27の利用者指定により、学生の学年は候補検索に使わない。任意のターム・曜日・時限にある教養科目の表示と、不足単位を補う効果の探索は別APIとする。単位集計の学年別表示とは分離する。
- 開講期間・曜日・時限が明確な通常授業だけを候補とし、集中講義・未定・空欄・解釈不能を除外する。
- 取り込んだ曜限は変更されない前提。対象年度・タームの選択は必要で、過年度の開講情報を現在のものとして流用しない。
- 取得・生成する科目データはGit管理対象外とする。
- 履修表の開講番号は先頭2桁を20YY年度、次の1桁をタームとして扱う。0の科目は利用者指定のMVP方針で占有時間から除外する。ただし、公式資料には0でも通常の曜限を持つ例があるため、集中講義の公式判定と同一視しない。

## 2. 実装済みの画面分離とメモリ共有

同じフロントエンドアプリ内で「単位集計」と「教養科目の履修推薦」の画面を切り替え、上位のメモリ上の状態を共有する方法を推奨する。タブやクライアント側ルーティングのどちらにするか、フレームワークを何にするかはフロントエンド担当が決められる。

```text
同じフロントエンドアプリの共有状態（メモリのみ）
  ├─ 成績CSVのFile、解析結果、選択した規則プロファイル
  ├─ 履修表CSVのFile、選択した開講年度・ターム
  ├─ 単位集計の画面
  └─ 教養科目の履修推薦の画面
           │ 必要な入力をその都度送る
           ▼
バックエンド：集計APIと推薦APIを別の入口にする
  └─ CSV解析・分類・学務判定は共通部品を利用
```

現在の`static/app.js`は`selectedFile`と`report`をメモリ上に保持し、元Fileを共有状態にも渡す。画面を分けるためのサーバーセッションは不要である。

参考UIは`static/navigation.js`でDOMを表示・非表示にし、`static/app.js`と`static/timetable.js`がそれぞれの入力と結果をメモリに保持する。元のFileだけは`static/workspace-state.js`で共有し、単位照合の探索に再利用する。マス検索は`static/recommendations.js`、単位照合は`static/recommendation-search.js`からそれぞれ独立したAPIを呼ぶ。共有状態は独自フロントの上位状態管理へ置き換えてよい。詳しくは[履修表の参考UI](timetable-csv.md#5-フロントエンド担当向けの参考ui)を参照する。

### 保持期間と制約

- 同じアプリ内の画面切り替えでは、共有状態を破棄しない。
- ページの再読み込み、タブを閉じる操作では学生データが消える。復元する場合は再アップロードする。
- 別のHTMLへ通常のページ遷移を行うとJavaScriptのメモリは引き継がれない。共有状態を使う場合は、アプリ全体を再読み込みしない画面切り替えにする。
- LocalStorage、SessionStorage、IndexedDB、永続化プラグイン等へ学生データを保存しない。SessionStorageもメモリ上の共有状態の代わりにはしない。
- 学生データをURL、クエリ、ルートのパラメーター、履歴のstateへ載せない。
- CookieにセッションIDだけを入れても、解析結果を保持する場所は別途必要になる。今回、そのためのサーバー側保存や共有キャッシュは導入しない。

## 3. フロントエンドとバックエンドの境界

フロントエンドは入力選択、画面切り替え、メモリ上の状態、通信、表示を担当する。推薦順位、要件の不足、曜限の重複判定はバックエンドが返す。

集計APIと推薦APIは分けるが、API間でレポートIDやサーバーセッションを共有しない。初版では、推薦を要求する際にメモリ上の元CSVを必要に応じて再送し、バックエンドの共通解析処理を再利用する方法を推奨する。フロントエンドから渡された総合判定や取得単位を、そのまま判定済みの正本として信用しない。

新しい成績CSV・規則プロファイル・履修表・対象タームへ変更した場合は、古い推薦結果を無効にする。並行リクエストの古い応答で新しい状態を上書きしない。未確定の履修中科目を、実際の取得済み単位へ加算しない。

履修表の入力は`POST /api/v1/timetables`の`file`にCSVを送る契約とする。詳細は[履修表CSVの読み取り仕様](timetable-csv.md)を参照する。候補取得のAPIとはリソースを分け、`POST /api/v1/reports`や`POST /api/v1/timetables`を候補取得APIとして案内しない。

現在の候補取得は`GET /api/v1/recommendation-catalogs`と`POST /api/v1/recommendations`で提供する。[候補API仕様](recommendation-api.md)を分業時の契約とする。CSVなしはカタログ検索、CSVありは元の履修表を毎回送って全曜限を検証する。セッションや解析結果ID、フロントの解析JSONを正本にする仕組みは導入しない。

修得単位との照合は`POST /api/v1/recommendation-searches`で提供する。成績CSVと履修表CSVを受け、全学年共通で卒業の教養関連単位条件を参照する。共通判定器で各候補を1科目ずつ仮追加し、改善する条件の不足を返す。修得済みは番号または正規化した科目名で除外する。確定した不足への候補と要確認の候補を分け、合計・分類別の改善量を合算しない。詳細な契約と確認範囲は[単位照合の探索API](recommendation-search-api.md)に記載する。順位付け・複数候補の組合せ最適化は未実装。

## 4. 開講データと学生データの分離

| 種類 | 保存・Git管理 |
| --- | --- |
| 学生の成績・履修表CSV、解析結果 | リクエスト処理中と画面利用中のメモリのみ。保存しない |
| 公式資料から取得した推薦用カタログ、抽出結果 | `data/recommendations/`配下へ作成しGit対象外 |
| 入学年度別の学務規則・既存科目マスター | 既存の`rules/`配下でバージョン管理を維持 |
| カタログの検証・生成コード、スキーマ、自動テスト | Git管理。手動確認用の架空CSVはGit対象外とし、手渡しZIPで共有 |

公開の開講カタログだけをサーバー内で再利用することは、学生の解析結果をキャッシュすることとは異なる。入学年度の規則と開講年度のカタログを分け、同じ科目に複数の開講枠がある場合も保持する。

Dockerでは`data/`をイメージへ含めず、Composeで公開の`liberal-catalog.json`だけを読み取り専用で配置する。学生CSVの保存先を作ったり、`data/`全体をマウントしたりしない。

## 5. 公式資料の候補

取得方法の調査で確認した入口は次のとおり。2026年度の開設一覧からGコード1,228開講を抽出し、全ページの番号照合と代表行の目視確認を行った。対象者条件の複雑な表記は採用を保留する。成績との照合は既存の名前正規化に対応し、未知の別名や同等科目の推測は行わない。

- [教育基盤機構・授業科目関連](https://www.iess.niigata-u.ac.jp/intramural.html)：年度ごとの授業科目開設一覧、Gコード科目授業時間表。
- [2026年度授業科目開設一覧](https://www.iess.niigata-u.ac.jp/acpb/upload/20260327161315092692700.pdf)：科目区分、開講番号、単位、開講時期、曜限、主聴講対象等。
- [工学部・在学生向け資料](https://www.eng.niigata-u.ac.jp/student/)：専門の推薦には使わないが、履修表に曜日・時限がなく開講番号だけがある場合、登録済み専門授業の占有時間を特定する資料として必要になり得る。

教養だけを推薦する場合も、時間の重複を避けるには登録済み専門授業を含む時間割が必要である。

生成データの場所、契約、G限定の範囲、再生成手順は[教養開講カタログ](liberal-catalog.md)を参照する。利用者の簡素化要望により、現在は全学部向け・学年絞り込みなしの309開講から代表63開講へ絞ったschema version 3のJSONを1つ使う。旧版は保管し、出典は別管理する。公開シラバスはrobots.txtが自動取得を禁止しているため巡回せず、授業概要・成績評価方法を簡易JSONへ含めない。開講情報の整備と、授業内容の全文取得や履修許可判定を区別する。

## 6. 履修表入力の確認結果と残りの作業

利用者提供CSVを保存せずメモリで確認し、曜日×時限のグリッドから開講番号と占有時間を取得するアダプターを実装した。入力は既存の成績CSVと異なる。個人情報・実際の履修内容をfixtureや文書へ転記せず、架空データだけで再現テストする。

- 曜日は列見出し、時限は行見出しから取得でき、通常授業の時間特定のためだけに専門の開講一覧を別途用意する必要はない。
- 同じ曜日・時限の別ターム科目、同じ科目の複数曜日・時限を保持する。見出しと全体行数を固定しない。
- 0の科目の除外はMVP方針として分離し、除外した授業との重複を未確認とする注意書きを返す。
- 履修取消等をこの形式から区別する規則は確認できていないため、表示された通常科目を占有時間として読み取る。合格・単位修得とは扱わない。
- 開講カタログと成績の照合は、番号または明示的に正規化した科目名の一致に対応した。未知の別名、推薦順位、受講対象者条件の複雑な表記は引き続き未実装・要確認である。

既存の成績CSVには曜日・時限がないため、推薦にはこの履修表も必要である。将来、開講番号しかない別の履修表形式へ対応する場合は、時間割照合用データを別途用意する。

開講番号欠落、通常科目の時間割外配置、年度・タームと学期の不整合を「授業がない時間」として扱わない。未掲載曜日・時限も、確認済みの空き時間と断定しない。
