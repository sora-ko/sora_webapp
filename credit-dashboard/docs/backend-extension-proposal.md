# バックエンドの拡張案

作成日：2026-11-04。利用者との検討用であり、追加機能・優先順位・保存期間は未採用。既存の要件やAPI契約を変更する文書ではない。

同日追記：API契約の整備、既存条件を維持した309開講への拡充、固定20分の[短期セッション・解析結果復元](session-api.md)を実装した。[OpenAPI・型・架空応答例](../contracts/README.md)を参照する。両参考UIはリロード復元に対応する。利用者の回答により、全利用者で蓄積・共有する科目評価も採用する方針となった。以降の当初案に優先する決定と実装順序は[保存方式の計画](session-and-ratings-plan.md)にまとめる。SQLite・共有評価は2026-11-11の指定で保留中であり、現在はセッションだけを仕上げる。

## 1. 方針

現在の単位集計・進級卒業の参考判定・教養の曜限閲覧・不足探索を土台に、フロントエンド担当が独立して接続できる機能を追加する。まずはJSON管理のまま進められる拡張を優先する。

- 対象大学は新潟大学、工学部内の拡張を優先する。別年度・プログラムの学務規則は公式資料から個別に確認する。
- 教養推薦は引き続き学年で絞らず、教養条件が充足していれば教養を推薦しない。
- 学生のCSV・解析結果は現行の非保存方針に従う。セッション復元だけは、別途保持方針を決めてから実装する。
- フロントエンドは学務判定を再実装せず、判定・説明・探索結果をAPIから取得する。
- 変更した入力・出力・境界値には、架空データによるテストと契約文書を付ける。

## 2. 優先順位

| 案 | 優先度 | 利用者・共同開発への価値 | フロントエンドとの調整 |
| --- | --- | --- | --- |
| API応答の型・機械可読スキーマ | P0 | 項目名、型、null、三値状態、エラーを正確に共有できる | 既存応答を維持する範囲では動作変更不要。契約を共有する |
| 候補カタログを63から309開講へ拡充 | P1 | 同じ時限・区分でも科目を選べる幅が広がる | 既存形式を維持できる。件数増に伴う操作性は確認する |
| 科目詳細・検索API | P1 | 授業内容や興味から候補を比較できる | 詳細画面・検索操作の接続が必要 |
| 複数科目の仮履修シミュレーション | P1 | 選んだ科目の組合せで不足がどう変わるか分かる | 科目選択と試算結果の表示が必要 |
| 単位配賦の科目別明細 | P1 | どの科目がどの枠に何単位使われたか追跡できる | 明細を開く表示が必要 |
| 推薦候補の並び替え | P2 | 不足区分や本人の希望に合う候補を見つけやすくする | 表示順の意味と操作を合意する |
| カタログ更新の差分検証 | P1・保守 | 年度更新で開講・曜限・分類の変更を見落としにくくする | 主にバックエンド・データ整備で進められる |
| 別入学年度・工学部内の別プログラム | P2 | 対象学生を広げる | 規則一覧から選ぶ現在の境界を使い、表示も確認する |
| 学期・区分別の成績分析 | P2 | 修得の推移や成績傾向を確認できる | 分析結果の表示が必要 |
| リロード後のセッション復元 | 保持要件決定後 | 再アップロードの手間を減らす | 起動時の復元・期限切れ・クリアの対応が必要 |

P0は分業の基盤、P1は次の機能候補、P2はその後の検討とする。学務規則の検証は対象拡張より先に行う。

## 3. 最初に進めやすい作業

### API契約の整備

既存JSONの形を変えずに、レポート・履修表・候補・探索・エラーの応答スキーマを作る。必須項目、列挙値、nullを許す箇所を定義し、架空のAPI応答例を添える。フロントエンドの技術選択は制限しない。

完了条件は、既存APIの成功・空・要確認・エラー応答がスキーマ検証を通り、文書と実際の応答に差がないこと。これは[バックログ](backlog.md)のAPI-002を具体化する案である。

### 候補の拡充と性能の確認

現行の63開講は、条件に合う309開講から代表を選んだ集合である。代表選定を任意にし、同じ安全条件で309開講を利用できる生成方法を追加する。G以外の科目や複雑な聴講指定へ範囲を広げる作業は別に根拠確認する。候補のない時間枠を推測で埋めない。

不足探索は候補を1科目ずつ仮追加して評価するため、63と309の両方で処理時間を計測する。必要があれば年度・ターム・区分・全曜限の事前絞り込みや、公開カタログの索引を改善する。学生の解析結果を長期間キャッシュする改善は混ぜない。

完了条件は、科目数を増やしても既存の取得済み除外・全曜限確認・教養充足後の推薦停止・unknownの扱いを維持し、処理時間と応答サイズを記録すること。

## 4. 科目を選ぶための機能

### 科目詳細と検索

候補一覧には基本情報を返し、詳細を開いたときに授業概要・到達目標・キーワード・評価方法などを取得する。確認できた項目だけを登録し、未確認を空想した内容で補わない。対象年度・公式資料との対応は管理用に保持する。

APIの形の例（未実装）：

- `GET /api/v1/courses?academic_year=2026&term=3&category=...&q=...`
- `GET /api/v1/courses/{course_code}?academic_year=2026`

授業内容の収集方法が前提になる。現行方針に沿い、利用可能な公式資料や手動整理など、取得可能な方法を確認する。DBの導入だけでは本文を取得できない。

既存の6項目カタログへ無条件に項目を足さず、ファイルのスキーマと公開APIの契約を分けて更新する。JSONからDBへ変更する場合も、フロントエンドが使う契約は独立して維持する。

### 複数科目の仮履修

成績CSV・必要に応じた履修表CSV・選択した開講番号を受け、すべてを仮に修得した場合の単位条件を既存の評価器で一度に再計算する。元の修得状況は変更しない。

現在の1科目ずつの効果を足し合わせる実装にはしない。複数科目が同じ不足を補う場合や、科目同士の時間重複をまとめて確認する必要があるためである。

返す情報は、条件別の変更前・変更後、仮追加された単位、未解決の条件、選択科目同士・登録授業との時間重複。試算は単位条件の変化であり、履修許可・合格・将来の卒業を保証するものではない。未確認の履修上限や先修条件を推測で制約へ加えない。

APIの例（未実装）：`POST /api/v1/course-simulations`。初期案は元CSVをリクエストごとに検証するため、DBや学生データの保存を前提にしない。

### 配賦明細と候補の表示順

現行の条件別合計に加え、科目ごとの使用先・使用単位・残りの単位・振替理由を返す。総計などの集約条件と、排他的な配賦枠を区別し、集約値を再加算しない。

推薦の表示順は、本人が選んだ区分や、確認済みの必修・選択必修不足などを優先する案が考えられる。ただし、これはアプリの表示方針であり公式の学務規則ではない。重複する分類別条件・教養合計・総計の改善量を単純に足した点数を作らない。確定候補と要確認候補は分けたままにする。

既存APIの開講番号順を突然変更せず、追加の並び替え指定などを契約化する。

## 5. 対象拡張・分析・復元

- **年度更新**：開講の追加・削除・曜限・単位・分類の差分を確認するCLIを追加する。学生データは入力にしない。変更点を確認してから新しい年度のデータを公開する。
- **別プロファイル**：[規則データ設計](rule-data.md)の制約とバックログRULE-006を先に確認する。新しい公式根拠、科目マスター、配賦・判定テストを追加し、既存年度を上書きしない。JSONの追加だけですべての分類体系に対応できるとは扱わない。
- **成績分析**：まず学期・区分別の修得単位など、利用者自身のCSVから計算できるものを提供する。GPAはCSVのGP・評語の意味、不算入科目等の公式ルールを確認してから追加する。成績予測に必要なデータを、利用者から無断収集しない。
- **セッション復元**：ランダムIDのCookieと、期限付きのサーバーメモリを使う案。現行APIは元CSVを毎回検証するため、復元後に探索も利用するには正規化済みデータから処理する入口が必要。保持項目・期間・破棄条件・アクセス分離を要件化し、合意後に実装する。Cookieへ成績を入れない。

## 6. 提案する進め方

1. APIのスキーマ・応答例を整えながら、309開講の生成と性能確認を進める。
2. 入手できる公式情報を確認し、科目詳細・検索APIを追加する。
3. 複数科目の仮履修と、単位配賦の明細を追加する。
4. 候補の表示順、別年度・プログラム、分析を必要に応じて広げる。
5. リロード復元は短時間保持の要件を別途確定し、上記の順序と独立して着手判断する。

前半はJSON管理と非保存APIで実装できる。公開カタログの共同編集・複雑な更新が必要になった段階でDBを検討する。公開カタログのDB化を、学生成績の永続保存への同意として扱わない。
