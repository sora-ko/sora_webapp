# アーキテクチャ方針

## 1. 目標

基準対象は2025年度入学・現在2年次・知能情報システムプログラム所属の学生本人で、localhostで利用する。同じ規則の1〜4年次表示、進級・卒業判定、教養候補検索・不足単位の探索は実装済み。将来のサーバー配置、別年度・プログラム、別分類体系、GPA分析を追加できる境界を維持する。
CSV形式、大学の規則、表示ロジックを分離する。

## 2. 論理構成

```text
Browser
  └─ Upload UI / Report UI
          │ multipart/form-data
          ▼
HTTP API
  ├─ rule profile registry / selection
  ├─ upload size / request validation
  ├─ CSV input adapter
  ├─ normalized transcript
  ├─ curriculum classifier
  ├─ supported requirement dispatcher / evaluator
  └─ versioned JSON response
```

処理は同期式で十分な規模とする。初回リリースではジョブキュー、ファイルストレージ、データベースを使わない。

## 3. 責務の分離

### CSV入力アダプター

- 文字コード、前置き行、列名、CSV上の値を解釈する。
- 出力は大学固有表記をなるべく排した正規化科目モデルとする。
- 卒業要件の数値を知らない。

### カリキュラム分類器

- 科目を教養系、専門基礎、専門応用、A〜E等へ分類する。
- 対象大学・入学年度・プログラム別のルールを使う。
- プロファイルの公開科目マスターを解析1回につき一度読み込み、既知の専門系科目へ名前索引で照合する。
- 一致時はマスターの科目群とA〜Eを採用し、一覧外の専門科目はプロファイルが明示したMVP方針で教養の選択へ分類する。原値と分類理由を両方保持する。
- 分類不能を明示し、推測で分類しない。
- 現在のMVPでは `classification.py` に置き、CSV構文の解釈を行う `parser.py` から分離する。

### 要件評価器

- 正規化・分類済み科目と、バージョン付き要件定義を入力にする。
- 進級・卒業要件ごとに充足、不足、不明と根拠を返す。
- 表示用の日本語HTMLを生成しない。
- CSVの学年から表示対象を選び、MVPでは留年・編入なしという明示的な前提の下で在学期間にも用いる。任意入力があれば上書きし、値の出所を結果に残す。
- 科目マスターの`required_for`を読み、卒業必修を1科目ずつ確認する。個別必修の確認単位は配賦・総計へ再加算しない。
- 個別必修も含めた全条件で総合三値を計算する。未知の入力が結果へ影響するときは`unknown`、確定した不足があれば`not_satisfied`、全条件充足なら`satisfied`とする。

### フロントエンド

- ファイル選択、送信状態、結果、警告、エラーを表示する。
- 単位や判定規則を再計算しない。
- 学生データをLocalStorage、SessionStorage、IndexedDBへ保存しない。

## 4. 規則のデータ化

判定値をPythonコードへ散在させず、次のキーで一意になる規則セットとして管理する。

```text
institution / faculty / program / admission_year / revision
```

現在学年は規則セットの識別子には含めず、どの判定や表示を有効にするかを決める評価コンテキストとして扱う。これにより、同じ2025年度規則を2年次から卒業まで再利用できる。

現在の配置:

```text
rules/niigata/engineering/smart-information-systems/2025/
  profile.json
  course-catalog.json
```

依存追加を避けるためJSONを採用し、`rules/profile.schema.json`と`academic_rules.py`で検証する。規則には公式資料の冊子ページとPDFページを持たせる。ファイルが肥大化した場合は同一スキーマのまま分類・進級・卒業へ分割する。

`GET /api/v1/rule-profiles`が登録済みプロファイルを列挙し、`POST /api/v1/reports`は`profile_id`で選択する。クライアントからファイルパスを指定させず、検証済みIDからサーバー内のプロファイルを解決する。現在の学年はプロファイル選択には使わず、在学期間などと同様に判定コンテキストとして別に扱う。

新しい年度・プログラムを追加する基本単位は、既存ファイルを変更しない新規プロファイル、公式根拠、分類テスト、対応する要件評価テストである。画面の対象文言はAPIメタデータから生成し、特定プログラム名を判定ロジックへ再埋め込みしない。

`classification.course_catalog_path`は`rules/`配下の相対パスに限定し、マスターの`profile_id`を選択プロファイルと照合する。名前はNFKC正規化と空白除去を照合時だけ適用し、別名の衝突はエラーにする。科目マスターIDは分類の根拠として保持し、単位数の上書きや同名・異コード科目の名寄せには使わない。

大学と科目名に依存する情報、対象外ラベル、一覧外の分類方針、画面のMVP注意書きはJSON側へ置く。個別必修は`required_courses`条件が、選択プロファイルの科目マスターで当該要件IDを`required_for`に持つ項目から生成する。空の必修一覧や単位数未確定の必修定義を、全科目充足として受け入れない。対象大学は今後も新潟大学だが、他学部の科目一覧・分類・要件を差し替えられる境界を維持する。A〜E以外の制度や別の進級節目へ対応するには、`docs/rule-data.md`に記録した評価器の制約を改修する必要がある。

## 5. 採用技術と判断（2026-10-22）

サーバーフレームワークにFastAPI、ASGIサーバーにUvicornを採用した。multipartの構文解析にはpython-multipartを使用する。

採用バージョンは`requirements.txt`を正本とする。APIテストにはpytestとhttpx2を使用し、`requirements-dev.txt`で管理する。

採用理由:

- APIルーティング、構造化エラー、ミドルウェア、静的ファイル配信を小さい実装で分離できる。
- ASGIアプリケーションとして将来の認証、リバースプロキシ、並行リクエストへ拡張できる。
- 実アプリを直接呼び出すAPIテストを作成できる。

トレードオフ:

- 依存パッケージの更新・脆弱性確認が継続的に必要になる。
- 通常のFastAPI `UploadFile`はサイズによって一時ファイルへ退避し得る。このプロジェクトでは使用せず、リクエストをpython-multipartでストリーム解析して5 MiBで中断し、CSV本文をメモリだけに保持する。
- テストクライアント周辺のライブラリ変更に追随する必要があるため、テスト依存もバージョン固定する。

## 6. 保存方針

- 学生のCSV・解析結果: 保存しない。公開の学務規則と開講カタログは学生データと分けて配置する。
- 解析中: 受信バイト列と正規化データをメモリに保持する。
- レスポンス後: サーバー側参照を破棄する。
- 将来DBを導入する場合: CSV原本ではなく、目的に必要な最小項目だけを保存候補とする。
- DB導入前に、同意、保存期間、暗号化、バックアップ、エクスポート、削除を要件化する。

## 7. デプロイ境界

### localhost

- 既定では `127.0.0.1` のみにbindする。
- 外部ネットワークへ通信せず動作する。
- コンテナー利用は任意とする。
- 学生本人による個人利用を前提とし、MVPでは認証を設けない。

### サーバー

- アプリケーションを直接インターネットへ公開しない。
- HTTPS終端、リクエストサイズ制限、タイムアウト、レート制限をリバースプロキシでも設定する。
- 複数利用者のリクエスト間でデータを共有しない。
- 認証が必要かを運用要件として決める。

## 8. 分析・推薦機能の境界

- GPA分析は要件評価器とは別の分析サービスにする。
- 実装済みの教養探索は、要件の不足と公開開講カタログ・履修表を照合する。順位付けや履修計画の最適化はこのAPIの上へ追加する。
- 成績予測は統計・機械学習機能として隔離し、学習データの出所と同意を必須にする。
- 予測結果を進級・卒業の確定判定へ混ぜない。

## 9. 教養推薦と画面の分離（2026-10-27時点）

2026-10-27の利用者指定により、教養候補の検索では学年を使わず、開講年度・ターム・曜日・時限で検索する。カタログは年度・プロファイルごとに共用する。全曜限の重複確認と実装済みの不足単位への効果計算はバックエンドに置く。単位集計で表示要件を選ぶ学年とは独立している。

不足単位の探索は`recommendation_search.py`と`POST /api/v1/recommendation-searches`へ分けた。成績・履修表のパーサー、既存の時間重複判定、卒業要件評価器を再利用する。各候補だけを仮追加して不足の変化を比較し、実際の成績や単位合計を書き換えない。2種類のCSVは共通のサイズ制限付きmultipart受信でメモリ処理する。フロントの共有状態は元のFileと対象プロファイルの公開メタデータで、サーバーセッションは不要。契約は[単位照合の探索API](recommendation-search-api.md)。

対象プロファイルは単位集計で選択し、`workspace-state.js`から教養候補へ共有する。推薦側のプログラム選択欄は設けず、対象名・入学年度・開講年度を表示する。履修表解析済みならその選択年度に一致するカタログ、未解析なら同一プロファイルの最新カタログを使う。未対応対象や年度不明を別カタログへ読み替えない。設定変更は結果を無効にし、遅れて届く旧応答も破棄する。

利用者指定により、推薦は教養科目・期間と曜限が明確な授業に限定する。確定した範囲と残る未確認事項は[推薦機能の設計メモ](recommendation-design.md)を参照する。現在は履修表の読取APIに加え、独立した候補APIで曜限検索と全曜限の重複除外を提供する。不足単位に基づく順位付けは未実装である。

集計と推薦は機能・APIとして分け、画面は同一フロントエンドアプリ内の共有メモリを使う方法を推奨する。画面を分けるためだけに、学生の解析結果をサーバーセッションや永続キャッシュへ保存しない。通常のHTML遷移や再読み込みではメモリが消えるため、再読込を伴わない画面切り替えと、再読み込み後の再アップロードを基本案とする。

公開資料からの生成は`catalog_import.py`、`offering_catalog.py`、`scripts/build_liberal_catalog.py`に分離する。年度別設定は`catalog_sources/`、原本・生成データは`data/recommendations/`へ置く。実行用の公開JSONと調査READMEだけをGit管理し、原本・抽出キャッシュ・旧版は除外する。実行時は`recommendations.py`で簡易カタログを検証・選択し、学生の履修表をメモリで照合する。PDF依存はサーバーへ加えない。Composeは公開JSON1ファイルだけを読み取り専用でマウントする。データ契約は[候補API仕様](recommendation-api.md)を参照する。

バックエンドAPIは参考UIのDOM・グローバル変数に依存せず呼び出せる。一方、従来UI内部には画面ID・イベント・共有変数への依存が残るため、各JSを独立したUI部品として再利用できるとは限らない。分業時は[引き継ぎ手順](handoff.md)のAPI境界を契約とし、UI内部の整理と機械可読な応答スキーマの整備は保守課題として扱う。

2026-10-28に`static/prototype/`へ、契約文書と公開APIから別の試作UIを追加した。既存UIのグローバル変数やバックエンドモジュールへ依存せず、独自のメモリ状態と通信クライアントで接続する。実装・契約の不足項目・31件のブラウザー確認は[試作記録](prototype-handoff-test.md)を参照する。
