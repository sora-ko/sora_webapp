# アーキテクチャ方針

## 1. 目標

最初は2025年度入学・2年次・知能情報システムプログラム所属の学生本人がlocalhostで利用する。将来はサーバー配置、対象年度・学年・プログラム、判定規則、履修推薦、GPA分析を追加できる構成とする。
CSV形式、大学の規則、表示ロジックを分離する。

## 2. 論理構成

```text
Browser
  └─ Upload UI / Report UI
          │ multipart/form-data
          ▼
HTTP API
  ├─ upload size / request validation
  ├─ CSV input adapter
  ├─ normalized transcript
  ├─ curriculum classifier
  ├─ requirement evaluator (release 2)
  └─ versioned JSON response
```

処理は同期式で十分な規模とする。初回リリースではジョブキュー、ファイルストレージ、データベースを使わない。

## 3. 責務の分離

### CSV入力アダプター

- 文字コード、前置き行、列名、CSV上の値を解釈する。
- 出力は大学固有表記をなるべく排した正規化科目モデルとする。
- 卒業要件の数値を知らない。

### カリキュラム分類器

- 科目を教養系、専門基礎、専門応用、A〜E等へ分類する。
- 対象大学・入学年度・プログラム別のルールを使う。
- 分類不能を明示し、推測で分類しない。
- 現在のMVPでは `classification.py` に置き、CSV構文の解釈を行う `parser.py` から分離する。

### 要件評価器

- 正規化・分類済み科目と、バージョン付き要件定義を入力にする。
- 進級・卒業要件ごとに充足、不足、不明と根拠を返す。
- 表示用の日本語HTMLを生成しない。

### フロントエンド

- ファイル選択、送信状態、結果、警告、エラーを表示する。
- 単位や判定規則を再計算しない。
- 学生データをLocalStorage、SessionStorage、IndexedDBへ保存しない。

## 4. 規則のデータ化

判定値をPythonコードへ散在させず、次のキーで一意になる規則セットとして管理する。

```text
institution / faculty / program / admission_year / revision
```

現在学年は規則セットの識別子には含めず、どの判定や表示を有効にするかを決める評価コンテキストとして扱う。これにより、同じ2025年度規則を2年次から卒業まで再利用できる。

例:

```text
rules/niigata/engineering/smart-information-systems/2025/
  metadata.yaml
  course-classification.yaml
  progression.yaml
  graduation.yaml
```

設定形式は実装時にJSONまたはYAMLから選ぶ。スキーマ検証と、公式資料のページ番号を各規則に持たせる。

## 5. 採用技術と判断（2026-10-22）

サーバーフレームワークにFastAPI、ASGIサーバーにUvicornを採用した。multipartの構文解析にはpython-multipartを使用する。

採用バージョンは`requirements.txt`を正本とする。APIテストにはpytestとhttpx2を使用し、`requirements-dev.txt`で管理する。

採用理由:

- APIルーティング、構造化エラー、ミドルウェア、静的ファイル配信を小さい実装で分離できる。
- ASGIアプリケーションとして将来の認証、リバースプロキシ、並行リクエストへ拡張できる。
- 実アプリを直接呼び出すAPIテストを作成できる。

トレードオフ:

- 依存パッケージの更新・脆弱性確認が継続的に必要になる。
- 通常のFastAPI `UploadFile`はサイズによって一時ファイルへ退避し得る。このプロジェクトでは使用せず、リクエストをpython-multipartでストリーム解析して5 MiBで中断し、CSV本文をメモリだけに保持する。
- テストクライアント周辺のライブラリ変更に追随する必要があるため、テスト依存もバージョン固定する。

## 6. 保存方針

- リリース1: 何も保存しない。
- 解析中: 受信バイト列と正規化データをメモリに保持する。
- レスポンス後: サーバー側参照を破棄する。
- 将来DBを導入する場合: CSV原本ではなく、目的に必要な最小項目だけを保存候補とする。
- DB導入前に、同意、保存期間、暗号化、バックアップ、エクスポート、削除を要件化する。

## 7. デプロイ境界

### localhost

- 既定では `127.0.0.1` のみにbindする。
- 外部ネットワークへ通信せず動作する。
- コンテナー利用は任意とする。
- 学生本人による個人利用を前提とし、MVPでは認証を設けない。

### サーバー

- アプリケーションを直接インターネットへ公開しない。
- HTTPS終端、リクエストサイズ制限、タイムアウト、レート制限をリバースプロキシでも設定する。
- 複数利用者のリクエスト間でデータを共有しない。
- 認証が必要かを運用要件として決める。

## 8. 将来機能の境界

- GPA分析は要件評価器とは別の分析サービスにする。
- 履修推薦は、要件上不足している枠と科目マスターを入力とする。
- 成績予測は統計・機械学習機能として隔離し、学習データの出所と同意を必須にする。
- 予測結果を進級・卒業の確定判定へ混ぜない。
