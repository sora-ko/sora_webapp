# 短時間セッション・共有評価の保存方式

更新日：2026-11-11。利用者との合意と、段階ごとの実装状況を記録する。APIの追加は各段階の実装時に契約へ反映する。本書にある未実装の機能を、現行フロントエンドが利用できるとは扱わない。

2026-11-11の利用者指定により、SQLite・共有評価・評価による順位付けは保留とし、現在の作業範囲をセッションの仕上げに限定する。実行コードにSQLite・評価APIは導入されておらず、巻き戻しは不要。以下のDB・評価に関する設計案は記録として保持するが、再開の指示なしに実装へ進まない。

## 1. 利用者が決定した内容

- ログイン認証を設けず、Cookieを使う短時間セッションを導入する。
- 成績・履修表の解析結果をサーバーのメモリだけに保持し、リロード後に復元できるようにする。CSV原本と解析結果をSQLiteやファイルへ保存しない。
- 科目への評価は、全利用者で蓄積・共有し、推薦に活用する。セッション終了時に評価も消す方式にはしない。
- 一度に組み込まず、機能ごとに実装・検証する。
- 有効期限は操作の有無にかかわらず作成から約20分とする。初期案の「操作なし30分・最大2時間」は採用せず、GET・POST等で期限を延長しない。

## 2. SQLiteの適用範囲

| データ | 採用する方式 | 理由 |
| --- | --- | --- |
| 公開の開講カタログ | 既存のJSONを維持 | 読み込み中心で、Git上で追加・変更を確認できる。既存の検証・年度・プロファイル照合をそのまま使える |
| 利用者の科目評価 | 導入保留。再開時の候補はSQLite | トランザクションと一意制約で同時投稿・更新・削除を扱え、件数・平均の集計をSQLへまとめられる |
| 短時間セッションと解析結果 | サーバーメモリに限定 | 有効期限後・明示終了・再起動で破棄し、成績情報をDBへ残さない |

共有評価までJSONで更新すると、同時書き込みの排他、書きかけファイルの回避、投稿の更新、集計を自前で実装する必要がある。SQLiteなら`UNIQUE`・`UPSERT`・`COUNT`・`AVG`などを使える。Pythonの`sqlite3`が使えるため、初期実装で別のDBサーバーやORMを追加する必要もない。

一方、公開カタログをSQLiteへ全面移行すると、初期データの投入・更新・移行処理が増える。今回の目的ではカタログのJSONを維持し、評価の書き込みだけをDBへ分ける方が変更を小さくできる。これは設計上の判断であり、実装行数や性能が既に改善したという測定結果ではない。

参考：[Python sqlite3](https://docs.python.org/3/library/sqlite3.html)、[SQLiteの適用範囲](https://www.sqlite.org/whentouse.html)。

次の作業を、個別に実装・検証できる単位へ分ける。公開カタログ拡充と機械可読API契約の整備は完了済み。現在の保存方式は公開科目JSONとセッションのメモリ保持だけであり、DBは導入しない。共有評価の設計案と全面SQLite移行の比較は保留中の検討記録とする。

| 2 | SESSION-002 | 解析結果の保持・復元（実装済み） | メモリ限定の成績・履修表復元と不足探索。両画面の再読込、期限、再アップロード、対象変更、容量制限、遅延応答を検証 |

各段階で関連テストと既存APIとの互換性を確認し、OpenAPI・TypeScript型・架空応答例・引き継ぎ文書を更新してから次へ進む。フロントエンドでセッションや学務判定を独自に推測する必要のない応答を提供する。フロント担当の作業範囲は、契約に沿った呼出し・状態管理・表示とする。

### 1. 公開カタログの拡充（実装済み）

現行の6項目・schema version 3を保ち、既存と同じ抽出条件に合う309開講へ拡充した。科目名の完全一致では186種類。旧代表63開講の生成は`--selection representative`で再現できる。通常は`--selection all`を使う。

カタログ・抽出・候補検索・不足探索の回帰テストを行い、APIのフィールド・型を維持する。学年での除外、未知区分の推測、集中・曜限不明科目の採用は追加しない。

### 2. 短時間セッションと解析結果の復元（実装済み）

SESSION-001の`POST/GET/DELETE /api/v1/session`に続き、SESSION-002として解析済みの成績・履修表のメモリ保持・復元、復元結果からの候補検索・不足探索を追加した。既存のCSVアップロードAPIはCookieなしで利用できるまま保持した。両画面のリロード復元を実装し、通信クライアントをDOMに依存しない`static/session-client.js`へ分離した。契約と接続方法は[短時間セッションAPI](session-api.md)を参照する。

- Cookieには暗号学的乱数の不透明な識別子だけを入れ、成績・学籍番号・氏名を入れない。`HttpOnly`、適切な`SameSite`、本番HTTPSでの`Secure`を使う。
- 利用者の追加指定により作成から固定20分。操作・再取得では延長しない。期限はサーバー側で管理し、Cookieの有無やブラウザーの終了だけに依存しない。
- 期限切れの参照を拒否し、定期的にメモリを掃除する。明示終了・サーバー再起動でも破棄する。
- セッション数と解析結果の合計サイズに上限を設ける。他利用者の結果へアクセスできないことをテストする。
- 状態変更にはCSRF対策を設ける。別Originの開発では許可Originと資格情報付きfetchを明示する。
- 復元対象は解析済みの成績・履修表。元CSVバイト列、教員行、不要な入力情報を保持しない。全応答の`Cache-Control: no-store`と非ログ方針を維持する。
- 初版は単一サーバープロセスを前提とし、複数ワーカーでメモリが分離されることを運用文書へ記載する。

SESSION-001では固定期限、利用者分離、明示終了、CSRF、セッション数上限、定期削除、停止時破棄を検証した。SESSION-002では架空データの再取得・対象変更・保持容量上限・削除後の遅延応答・アップロード失敗・競合を検証し、CSV・解析結果がファイルやDBへ保存されないことも確認した。解析結果の保持上限は既定で1セッション8 MiB・全体64 MiB。リビジョン照合により、削除や期限切れの後に古い処理が結果を復活させない。

### 3. 共有評価の蓄積（保留中の設計案）

初期案は数値評価だけを扱い、自由記述は含めない。評価尺度・意味はAPI実装時に明示する。未評価を0点・低評価へ変換しない。

評価の識別には開講年度と開講番号を使う。別年度・別クラスの評価を、同じ科目名というだけで自動統合しない。年度をまたぐ統合が必要になったら、明示した科目対応表を別途設ける。

保存する最小情報の案は、開講年度・開講番号・評価値・更新用のランダムな投稿者識別子。同じセッションから同じ開講への再評価は追加投票にせず更新し、セッション内で取り消せるようにする。氏名・学籍番号・所属・成績CSV・解析結果・IPアドレスを評価テーブルへ入れない。SQLite本体・補助ファイル・バックアップはGitから除外する。

セッション失効後も共有評価は残る。ログインがないためCookie削除・別ブラウザー・新セッションによる再投稿を完全には防げず、実人数や1人1票を保証しない。初版の集計件数は評価件数であり、学生数と表記しない。古い評価の本人による再編集・削除方法と、評価の保持期間は、この段階で具体化する。匿名識別子だけでも評価履歴を関連付けられることに留意する。

完了条件：DBの一意制約、同時更新、入力範囲、未掲載科目の拒否、更新・取消・集計、学生データを永続化しないことをテストする。

### 4. 共有評価を使った推薦（保留中の設計案）

まず既存の評価器で不足と時間重複を確認し、その候補の表示順へ共有評価を反映する。共有評価は、学務上の算入可否・履修許可・合格可能性の根拠にはしない。判定不能の候補は確定候補から分けたままにする。

評価件数と平均を併記し、少数評価を過大に扱わない順位付けを検討する。未評価にも選択肢としての機会を残し、同点は開講番号等で順序を安定させる。教養が充足していれば不足推薦を出さない現行方針を維持する。

完了条件：既存の単位判定・除外条件が変わらず、評価なし・少数・同点・更新後の順位と説明が契約に一致することをテストする。

## 4. 現在の提供状態

公開カタログ309開講、短期セッション、解析結果の保持・復元を実装した。`/`と`/prototype/`の両画面で再読み込み後に成績・履修表を復元でき、CSVを再送せず不足探索を行える。SQLite・共有評価の投稿・評価順のAPIはまだ追加していない。既存APIは引き続きセッションなしで利用できる。

ログインなしの識別子は、本人確認や完全な匿名性を保証しない。セッションや共有評価の導入を、成績データの永続保存への承認として扱わない。
