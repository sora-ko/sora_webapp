# AIエージェント向け開発規約

## 1. 作業開始時

1. このファイルと関連する `docs/` の文書を読む。
2. 依頼された変更がどの要件・コンポーネントに関係するかを確認する。
3. 既存実装とテストを調べ、既にある機能を重複実装しない。
4. 仕様が未決定なら、影響が小さく可逆な仮実装を選び、推測を合意済み事項として記録しない。重要な判断が必要な場合は `docs/OPEN_QUESTIONS.md` に追加する。

## 2. 設計原則

- 単純な構成から始める。初期段階でマイクロサービスや過剰な抽象化を導入しない。
- 責務を分離する。UI、API、セッション管理、GDB/MI通信、状態データの正規化、対象プロセスI/Oを混在させない。
- フロントエンドからGDBプロセスを直接操作しない。
- GDBのコンソール表示やpwndbgの人間向け出力を、コア機能の唯一のデータソースにしない。基本情報はGDB/MI等の機械向けインターフェースから取得する。
- GDB固有の応答形式を画面コンポーネントへ漏らさず、バックエンドの共通データモデルに変換する。
- RBPが常にフレームポインタである、スタック上の各値の意味が必ず特定できる、などの仮定を置かない。不明な情報は不明と表示する。
- すべての新機能に、適切な自動テストまたは検証手順を追加する。
- 依存ライブラリを追加する場合は、必要性・保守性・ライセンス・実行時の影響を短く記録する。

## 3. 安全上の規約

- 利用者が指定したELFを実際に実行する機能であることを忘れない。実行ファイルの検査だけで安全性が保証されたと説明しない。
- 初期版はローカル利用を前提とし、原則 `127.0.0.1` にのみバインドする。明示的な設計レビューなしに `0.0.0.0` へ公開しない。
- `shell=True` や、利用者入力を連結して作るシェルコマンドを避ける。外部プロセスは原則として引数配列で起動する。
- 初期版で任意のシェルコマンドや任意のGDBコマンドを無制限に実行するAPIを追加しない。GUI操作は型付きの限定された操作にする。
- セッションID、ファイル名、アドレス、コマンド引数などを信頼済み入力として扱わない。
- テスト用ELFは専用の作業領域で扱い、ユーザーのホームディレクトリやリポジトリ内に不要な生成物を残さない。
- 脆弱なサンプルは意図的に脆弱なものとして明示し、テスト用であることを文書化する。
- 将来のサーバー公開を想定する場合、認証だけでなく、実行環境の隔離・リソース制限・ネットワーク制御を別途設計する。ローカル版の安全設計をそのままサーバー版へ流用しない。

## 4. 実装とテスト

- まず最小の変更で実装し、フォーマット・型チェック・静的解析・ユニットテスト・関連統合テストを実行する。
- 実行していないテストを「成功」と報告しない。環境上実施できなかったテストは理由と未確認範囲を明記する。
- GDB連携の変更では、正常応答だけでなく、実行中、停止中、終了済み、異常終了、応答タイムアウトを扱う。
- 非同期イベントやWebSocketを追加する場合、切断、再接続、古いイベント、二重処理をテストする。
- テストは実機の既存バイナリや利用者のファイルに依存させず、リポジトリ内の小さなテストプログラム・fixtureを使う。

## 5. 文書更新

- 要件や設計に影響する変更は、該当する文書を同じ変更で更新する。
- 重要な技術判断には `docs/decisions/NNNN-短い名前.md` を追加する。
- 決定記録には、状態（提案中／合意済み／廃止）、背景、選択肢、理由、影響、再検討条件を書く。
- ユーザーが決めた内容とAIの推奨を明確に区別する。

## 6. 完了時の報告

作業完了時は、次を簡潔に報告する。

1. 変更した内容
2. 変更理由
3. 実行したテストと結果
4. 未確認の点・既知の制約
5. 更新した設計文書

コードを書いただけで、動作確認を行っていない場合は、その旨を明示する。
