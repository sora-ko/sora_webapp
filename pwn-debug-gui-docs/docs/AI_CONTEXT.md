# AI向けプロジェクトコンテキスト

このファイルは、新しいAIチャットやAIコーディングエージェントにプロジェクトの背景を短時間で共有するための要約である。詳細や更新は他の設計文書を参照すること。

## ユーザーが明示した目的

- pwn初心者が学習を始めやすい、デバッグ状態を可視化するGUIを作りたい。
- AIとのバイブコーディングを中心に開発する想定。
- 最優先事項は、AIが直接開発を進められる環境、安全設計、将来の拡張に耐えられる分かりやすい設計。
- 約半年で、まず使える成果物を作りたい。
- AIにはコード生成だけでなく、事前情報・設計資料・不足情報の洗い出しを支援してほしい。

## 合意済みの製品方針

- 初期版は利用者自身のUbuntu / WSL環境で実行する。サーバー版は将来の選択肢だが、運用コストが大きければ断念してよい。
- ブラウザで使うWeb UIを想定している。
- 対象はx86-64 Linuxのコンパイル済みELF。
- 初期版はシンプルなコードの基本的なデバッグを可能にする。
- 6か月後の目標は、利用者が実際にバッファオーバーフローを起こし、スタック上の状態をGUIで確認できること。
- GDBを中心に操作し、pwndbgは拡張として扱う。
- 初期の基本フローは通常起動し、利用者が停止位置を指定すること。
- 特定アドレスのメモリ表示を用意する。ヒープ専用の高度な表示は初期版の優先事項ではない。
- アドレスに対応するシンボルやコード情報がある場合は表示を支援する。
- レジスタの基礎などの一般的な学習コンテンツは、デバッガーの中核機能とは分け、優先度を下げる。
- `pwninit` による依存ライブラリの取得・配置やpatchファイル生成は後回し。

## ELFの受け渡し方式

ユーザーはブラウザアップロードを希望している。ただし、アップロードの実装コストが大きい場合は、利用者がWSL内の指定ディレクトリに配置する方式でもよい。現時点で確定した扱いにせず、短い技術検証で比較して確定する。初期提案は、操作性と将来性を考慮してアップロード方式。

ユーザーは、知り合い限定の初期試用を想定しているため、高度なサニタイズやサーバー級の隔離設計を初期版で先行させることは望んでいない。AIはこれを「安全対策をしなくてよい」と解釈してはいけない。低コストの基本対策（localhost限定、適切な作業ディレクトリ、ファイル名管理、サイズ上限、シェル経由の危険な起動を避ける、セッション分離など）を採用し、公開サーバー向け対策は公開前に別設計とする。

## 設計上の優先事項

1. 明確な責務分担とインターフェース
2. AIが参照できる文書と作業規約
3. 自動テスト・統合テストによる検証可能性
4. セキュリティ境界を必要十分な形で維持
5. 将来の拡張を妨げないが、初期から複雑にしすぎない実装

## 最初に検証すべき技術的リスク

- GDB/MIの応答と非同期イベントの扱い
- GDBの制御用入出力と、対象プログラムのstdin/stdout/stderrを分離する方法
- `read()`、`scanf()`、TTY、バイナリ入力、改行、EOFの挙動
- WSL上のバックエンドとWindows側ブラウザの接続
- ELF単体では依存ライブラリ不足で起動できない場合の説明方法
- シンボルがないELFやPIEでのアドレス指定と表示

## AIへの重要な指示

- 決定済みの内容、推奨案、未決定事項を混同しない。
- 仕様の穴を見つけたら `docs/OPEN_QUESTIONS.md` に記録する。
- コードの都合だけでユーザー要件を黙って変更しない。
- 重大な技術判断はADRに記録する。
- 実行していないテストを通過したと報告しない。
- このファイルだけで仕様を判断せず、必要に応じて `PROJECT_CHARTER.md`、`REQUIREMENTS.md`、`ARCHITECTURE.md`、`SECURITY.md`、`DEVELOPMENT.md` を読む。
