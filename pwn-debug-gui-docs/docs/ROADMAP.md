# 6か月ロードマップ（初期案）

期間は目安であり、最初の技術検証と利用者の反応に基づいて調整する。AI開発基盤の整備とテストを後回しにしない。

## Phase 0 — 要件・基盤の準備

成果物:

- プロジェクト憲章、要求仕様、安全設計、アーキテクチャ案
- `AGENTS.md` とAI作業規約
- リポジトリ、環境構築手順、静的解析・テストコマンド
- GDB/MI + テストELFのPoC
- WSLとブラウザの接続検証
- ELF受け渡し方式と対象プロセスI/Oの技術検証

完了条件: 人間またはAIが手順に従って開発環境を再現でき、GDB/MIでテストELFの停止状態を取得できる。

## Phase 1 — 基本デバッグの縦切り実装

成果物:

- ELFを選択してデバッグセッションを作成
- セッション終了・クリーンアップ
- GDB起動と対象ELFのロード
- ブレークポイント、run、interrupt、continue、step
- エラーと実行状態の表示

完了条件: GUIからテストELFを起動・停止・ステップ実行できる。

## Phase 2 — デバッグ状態の取得

成果物:

- レジスタ表示
- 現在位置周辺の逆アセンブル
- 指定アドレスからのメモリ表示
- シンボルが得られる場合の名前表示
- 停止理由とプロセス終了状態の区別

完了条件: GUIの表示とGDBから取得した既知の値をテストで照合できる。

## Phase 3 — スタックとプログラムI/O

成果物:

- RSPを中心としたスタックビュー
- アドレス、バイト値、ワード値などの表示
- プログラムへの入力とstdout/stderr表示
- テキストとバイナリ入力の扱い方針
- 状態変更前後の比較

完了条件: テストプログラムの入力でスタック領域の値が変わり、その変化をGUIで追える。

## Phase 4 — オーバーフロー学習シナリオ

成果物:

- テスト専用の脆弱なCプログラムと再現手順
- 既知の入力を送信してオーバーフローを再現
- スタックの変更箇所を強調表示
- 不正アクセスやSIGSEGVなどの停止理由を説明
- シンボルやフレーム情報の確度を表示

完了条件: 初心者が手順に沿ってオーバーフローを起こし、何が変わったかをGUIから確認できる。

## Phase 5 — 安定化・試用

成果物:

- インストールと起動の簡易化
- 初心者向けエラー表示
- セッション漏れや子プロセス残留の検査
- テストとドキュメントの補完
- 知り合いによる利用テストとフィードバック

完了条件: 利用者が導入手順から始め、代表的なpwn用ELFで一連のデバッグ作業を完了できる。

## 意図的に後回しにする機能

- pwninit連携
- ライブラリの自動ダウンロードとpatchファイル生成
- 公開サーバー構築
- 高度なヒープ可視化
- 複数アーキテクチャへの対応

これらは、スタック可視化とオーバーフロー観察という最終目標が安定してから、需要に応じて再評価する。
