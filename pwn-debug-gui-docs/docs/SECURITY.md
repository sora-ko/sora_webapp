# セキュリティ設計

## 1. 脅威モデルと前提

初期版は、個人的な知り合いを中心に利用するローカルツールとして想定する。公開インターネット上で不特定多数に実行機能を提供するものではない。

ただし、アプリケーションの目的上、利用者が指定したELFを実行する。ELFは任意の命令を実行できるプログラムであり、悪意のあるファイルや誤操作により、利用者権限でファイル変更・外部通信・プロセス起動等が起こる可能性がある。形式検査で実行リスクを除去することはできない。

## 2. 初期版で採用する最小限の対策

1. **ローカル公開を既定にする**: バックエンドは原則 `127.0.0.1` のみで待ち受ける。LAN公開は明示的な変更とレビューなしに行わない。
2. **プロセス権限**: GDBと対象ELFを通常の利用者権限で起動し、`sudo` を要求しない。
3. **ファイル管理**: アップロード方式の場合はアプリケーション管理下の専用作業ディレクトリを使い、ユーザー入力のファイル名をパスに直接使用しない。
4. **セッション分離**: セッションごとに作業ディレクトリ、GDBプロセス、対象プロセスを紐付ける。他セッションの資源を参照・操作できないようにする。
5. **外部プロセス起動**: シェル文字列を組み立てず、引数配列でGDBや補助コマンドを起動する。
6. **コマンド面の制限**: 初期版では任意シェルコマンド実行機能を作らない。GDB操作は型付きの許可された操作としてAPI化する。
7. **入力制限**: ファイルサイズ、メモリ読み取り長、アドレス形式、引数長など、資源消費と異常入力に上限を設ける。
8. **終了処理**: セッション終了時に子プロセスを停止し、作業ファイルを適切に削除する。
9. **ローカルWebの境界**: ローカルサービスへの意図しないブラウザアクセスを減らすため、Host/OriginやCORS等を構成に応じて確認する。ローカルバインドだけであらゆる攻撃が防げると考えない。

これらは大規模な隔離基盤ではなく、低コストで維持すべき最低限の工学的対策である。

## 3. 初期版で過剰に行わないこと

- 初期版からマルチテナント向けの複雑な認証・権限システムを構築しない。
- 独立したマイクロVMや分散ワーカー群を先行導入しない。
- すべてのELFを静的解析で安全と判定しようとしない。

ただし、この方針は対象ELFが無害であるという意味ではない。利用者が信頼できるか判断したファイルだけを実行すること、実行するとそのファイルは利用者の権限で動くことを、UIやドキュメントで説明する。

## 4. アップロード方式の注意

アップロード処理は、ファイル転送そのものよりも保存場所・命名・サイズ制限・ライフサイクル管理を適切に実装することが重要。初期版で大規模なウイルス検査や複雑なコンテンツサニタイズを導入する必要はないが、最低限次を行う。

- サイズ上限を設定する。
- サーバー側でファイル名・保存先を決める。
- ELF形式およびアーキテクチャの検査結果を表示する。
- ファイル検査と実行時の安全性を区別する。
- アップロードしたファイルをWeb静的配信のディレクトリに保存しない。
- セッション終了後の削除・保持方針を定める。

## 5. 将来サーバー公開する場合に追加で必要な設計

サーバー版では初期版の対策だけでは不足する。公開前に別の脅威モデルと設計レビューを行い、少なくとも次を検討する。

- 利用者認証とセッション所有者の確認
- セッションごとに分離されたコンテナまたは同等の隔離
- CPU、メモリ、プロセス数、ファイル容量、実行時間の制限
- ネットワークアクセスの制限
- ホスト資源へのアクセス防止
- 監査ログ、異常終了処理、濫用対策
- 依存ライブラリと実行環境の再現性

ローカル版をインターネットへ公開するだけでサーバー版が成立する、という扱いにはしない。
