# アーキテクチャ設計

## ステータス

この文書は初期案。コンポーネント境界と基本原則を先に定め、使用ライブラリの確定は小規模な技術検証後に行う。

## 1. 全体方針

- 初期版はローカルWebアプリケーションとして、利用者自身のUbuntu / WSLで動かす。
- UIとデバッガー操作をHTTP / WebSocket等の明確なインターフェースで分離する。
- バックエンドは初期段階で単一プロセスとしてよいが、内部の責務はモジュールで分離する。
- GDB/MIの通信・解析をUIや一般API処理に分散させない。
- pwndbgの出力を中核のデータモデルにしない。

## 2. コンポーネント案

### Frontend

責務:

- ELFの選択・送信
- セッションの作成・終了
- 実行制御ボタンとブレークポイントの操作
- レジスタ、逆アセンブル、メモリ、スタック、対象プログラムのI/O表示
- バックエンドから届いた状態を表示すること

禁止事項:

- GDBのコマンド文字列を自由に構築して送信しない
- GDB/MIの応答文字列を直接解釈しない
- メモリやスタックについて、取得できていない情報を断定しない

### API Layer

責務:

- 入力の形式・サイズ・状態の検証
- フロントエンドの要求を型付きのバックエンド操作に変換
- エラーを一貫した形式で返す
- 状態更新イベントを配信する

候補となるエンドポイント（確定仕様ではない）:

- `POST /api/sessions` — セッション作成（ELFの受け取り方式は未確定）
- `GET /api/sessions/{id}` — セッション状態の取得
- `DELETE /api/sessions/{id}` — セッション終了
- `POST /api/sessions/{id}/run` — 実行開始
- `POST /api/sessions/{id}/interrupt` — 実行中断
- `POST /api/sessions/{id}/continue` — 継続実行
- `POST /api/sessions/{id}/step` — ステップ実行
- `POST /api/sessions/{id}/breakpoints` — ブレークポイント操作
- `GET /api/sessions/{id}/state` — レジスタ・命令位置等の状態取得
- `GET /api/sessions/{id}/memory?address=...&size=...` — メモリ取得
- WebSocket等 — 実行停止・出力・状態変更イベント

APIの具体的な形式は、GDB/MIと対象プロセスI/Oの技術検証後に確定する。

### Session Manager

責務:

- 一意なセッションIDの生成
- 各セッションにおけるELF、作業ディレクトリ、GDB、対象プロセスの紐付け
- 状態遷移と終了処理の管理
- タイムアウト・異常終了・切断時のクリーンアップ

### ELF Storage / Validator

責務:

- アップロードまたはローカルファイル選択の入口を抽象化する
- 保存先を管理する
- ファイルサイズ・形式・アーキテクチャを確認する
- 検査結果と実行可否を分けて報告する

### Debugger Adapter

責務:

- GDBプロセスの起動・終了
- GDB/MIコマンドの送信と応答の解析
- 非同期停止イベントの受信
- 実行状態の正規化
- タイムアウト、終了済みセッション、不正応答の処理

GDB/MIのトークンや非同期応答の対応付けを考慮し、複数操作が競合しないようにする。最初の実装では、1セッションにつきGDB操作を直列化する方式を検討する。

### State Normalizer / Memory Service

責務:

- GDB由来の値をUI向けの一貫したデータモデルに変換
- レジスタ名・値、命令アドレス・命令表現、メモリアドレス・バイト列を保持
- メモリ領域の読み取り失敗やアクセス不可能な領域を表現
- スタックの行表示や差分計算に必要な情報を提供

GUI向けモデルには、生データ、整形済み表示、解釈の確度を区別できる余地を作る。例えば、RSPはレジスタから取得した事実だが、「この値は戻りアドレス」といった意味付けは情報源により確度が異なる。

### Process I/O Service

責務:

- 対象プログラムの標準入力・標準出力・標準エラーを扱う
- GDBの制御用入出力と対象プログラムの入出力を分離する
- バイト列とテキスト表示を混同しない
- EOF、改行、TTY/パイプの違いを表現する

**初期の技術検証で最優先すべき領域**。GDBの制御チャネルと対象プログラムのstdin/stdoutを混ぜると、入出力が不安定になる可能性がある。特にpwnではバイナリ入力や改行の有無が重要なので、単なるテキストコンソールで十分かを早期に検証する。

## 3. 推奨技術スタック候補

未確定の提案:

- Frontend: React + TypeScript
- Backend: Python + FastAPI
- 双方向イベント: 初期はHTTPの要求・応答で足りる範囲から始め、必要な状態通知にWebSocketを導入
- Debugger: GDB/MI
- Optional: pwndbg
- テスト: Pythonのバックエンドテストに加え、実際のGDBを使う統合テスト

この選択はまだ合意済みではない。まずELFを起動して停止させ、レジスタとメモリを取得する小さなPoCを作り、技術的な難所を確認してから確定する。

## 4. 基本データモデル案

### DebugSession

- `id`: ランダムなセッション識別子
- `status`: `created | starting | running | stopped | exited | failed | terminated`
- `elf_metadata`: アーキテクチャ、形式、シンボル等の検査結果
- `debugger`: GDBプロセスの状態
- `target_process`: 対象プロセスの状態
- `created_at` / `last_activity_at`
- `workspace`: 内部作業ディレクトリの参照

### StopState

- `reason`: breakpoint / signal / step / interrupt / exited / unknown 等
- `pc`: プログラムカウンタ
- `registers`: レジスタ名と値の対応
- `disassembly`: アドレス、命令、必要に応じてシンボル情報
- `stack_pointer`: RSPの値
- `memory_regions`: アドレス、取得バイト列、読み取り可否
- `timestamp`または状態バージョン

値の単位、数値表現、エンディアン、メモリ取得失敗の扱いは実装開始前に共通化する。アドレスは表示時に16進数に整形しても、内部では一貫した型で扱う。

## 5. 状態遷移

基本状態案:

`created -> starting -> running -> stopped -> running ... -> exited`

異常時は `failed`、利用者終了時は `terminated` を使う。GDB停止と対象プロセス終了を混同しないこと。プログラムがSIGSEGVで停止した状態と、プロセスが正常終了した状態は別々に表現する。

## 6. 将来のサーバー化に備える境界

- フロントエンドとバックエンド間は明確なAPI契約にする。
- セッションIDだけから実行環境のパスを推測しない。内部管理データから解決する。
- ローカルのディレクトリやOSプロセスに依存するコードをSession Manager / Debugger Adapter / Process I/Oへ閉じ込める。
- 初期版ではサーバー向けのマルチテナント機能を実装しない。
- サーバー化時は別途、コンテナ等による隔離、資源制限、ネットワーク制御、認証、監視、利用上限を設計する。
