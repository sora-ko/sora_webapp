# 要求仕様

## ステータス表記

- **確定**: ユーザーとの会話で合意済み
- **提案**: 初期設計として推奨する。実装開始前に検証・承認する
- **未決定**: 追加の判断が必要
- **後回し**: 初期版では実装しない

## 1. ユーザー像と利用シナリオ

主な利用者はpwn初心者。利用者は自分のUbuntu / WSL環境でWeb UIを開き、コンパイル済みELFを指定し、プログラムを実行・停止・ステップ実行しながら、レジスタ・命令・メモリ・スタックの内容を確認する。

## 3. 初期版の推奨受け入れ条件

初期版の範囲を、まず次の動作で検証する。

1. 小さなテストELFを指定してセッションを作成できる。
2. GDBが正常起動し、セッションに対応するデバッグ対象をロードできる。
3. 関数名または命令アドレスによるブレークポイントを設定できる（シンボルがない場合はアドレス指定で検証する）。
4. 実行を開始し、ブレークポイントまたは明示的な割り込みで停止できる。
5. 停止状態でレジスタ、現在位置周辺の逆アセンブル、指定アドレスのメモリを取得できる。
6. ステップ実行後に情報を再取得し、変更が表示に反映される。
7. セッションを終了すると、GDBと対象プロセスが終了し、作業ファイルが適切に整理される。
8. ELFが不正・非対応・依存ライブラリ不足などのケースで、クラッシュせず説明可能なエラーを表示する。

## 4. 6か月目標の受け入れ条件案

1. リポジトリ内に専用の脆弱なCサンプルと、そのビルド手順・期待される挙動を置く。
2. GUIからサンプルに入力を渡し、入力内容に応じて停止・クラッシュ等が起きる様子を確認できる。
3. スタックビューでアドレスと値を表示し、少なくとも連続したメモリ領域を追跡できる。
4. 入力前後やステップ実行前後の変化を比較できる。
5. シンボルやフレーム情報が得られない場合は、確定情報と推定情報を区別する。
6. 実際に動作することを自動テストまたは記録された再現手順で確認できる。

## 5. 非機能要件

| ID | 要件 | 優先度 |
|---|---|---:|
| NFR-001 | Ubuntu / WSL上で再現可能な開発・実行手順を提供する | 必須 |
| NFR-002 | ローカル利用を既定とし、意図せずLANへ公開しない | 必須 |
| NFR-003 | フロントエンド、API、GDB連携の責務を明確に分ける | 必須 |
| NFR-004 | 主要ロジックに自動テストを用意し、AIが変更を検証できる | 必須 |
| NFR-005 | GDB/MIの生応答をUIコンポーネントから隠す | 必須 |
| NFR-006 | エラー時にセッション状態を壊さず、原因と復旧策を提示する | 必須 |
| NFR-007 | サーバー版への拡張を妨げないAPI境界を用意する。ただしサーバー版専用基盤を初期版で実装しない | 中 |
| NFR-008 | 重要な仕様・設計判断を会話ログではなく文書に保存する | 必須 |

## 6. 初期版では明確に保証しないこと

- 任意のELFが依存ライブラリ等の追加準備なしに起動すること。
- ソースコードのないELFで変数名や行番号を必ず表示できること。
- すべてのスタック値の意味を自動で判定できること。
- すべての入力方式（TTY、パイプ、バイナリデータ）を初期段階から扱えること。
- アップロードしたELFが無害であること。
