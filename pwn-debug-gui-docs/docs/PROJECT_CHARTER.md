# プロジェクト憲章

## ステータス

- 文書状態: 初版 / 継続更新中
- 目的: プロジェクトの意図と優先順位を、AIと人間が共有できる基準にする

## 1. 背景・課題

pwn初心者がGDBやpwndbgを使って学ぶ際、レジスタ、命令、アドレス、スタック上のデータの関係をテキスト出力だけから把握するのは難しい。本プロジェクトでは、デバッグ操作とメモリ状態の可視化を統合し、実行状態の変化をGUIで理解できるようにする。

## 2. 目的

コンパイル済みのx86-64 Linux ELFをデバッグし、実行状態、レジスタ、逆アセンブル、任意アドレスのメモリ、特にスタックの状態を視覚的に確認できるWeb GUIを作る。主な利用者はpwn初心者であり、pwnの学習を始めやすくすることを重視する。

## 3. 6か月後の目標

利用者が意図的に脆弱なサンプルELFを実行し、入力によってバッファオーバーフローを発生させ、スタック上のデータや制御に関係する値がどのように変化したかを、GUI上で追跡・理解できる。

「6か月後」は目標時期であり、すべての高度機能の実装を保証するものではない。機能の完成条件は受け入れテストとして具体化する。

## 4. 初期版の範囲

- 利用者自身のUbuntu / WSLで実行するローカルアプリケーション
- ブラウザから操作するWeb UI
- コンパイル済みx86-64 Linux ELFをデバッグ対象とする
- GDBを基本デバッガーとし、GDB/MIを主要インターフェース候補とする
- 起動、実行、停止、再開、ステップ実行、ブレークポイントなどの基本操作
- レジスタ、逆アセンブル、指定アドレスからのメモリ表示
- スタックの可視化を最終目標に向けて設計する
- AIが変更を加えても動作確認できるテスト環境と開発規約を整える

ELFのブラウザアップロードは現在の希望だが、ファイル受け渡し方式の実装コストを確認して最終決定する。ローカルディレクトリからの選択方式も代替案として残す。

## 5. 初期版で対象外とするもの

- 公開インターネット上でのマルチユーザー実行サービス
- サーバー実行基盤やクラウドの本番運用
- `pwninit` による環境構築、ライブラリ取得、patchファイル生成
- x86-64 Linux以外のアーキテクチャやOS
- 任意のデバッガーを一度に複数サポートすること
- 任意のシェルコマンド実行機能
- 高度なヒープ解析、ヒープ専用ビュー（ただし任意アドレスのメモリ表示は対象）
- 完全なexploit自動生成

## 6. 開発の優先順位

優先順位は次の順とする。

1. AIが作業内容と設計意図を理解し、検証可能な形で開発できること
2. セキュリティ上の境界と責務を明確にすること
3. シンプルで理解しやすく、将来の拡張点が明確な構造
4. 6か月後の学習体験につながる実用的な機能
5. 見た目の細部や追加機能

## 7. 成功の判断基準

初期版の成功:

- 既知の小さなELFをロードしてデバッグセッションを開始できる。
- 基本的な実行制御をGUIから行える。
- 停止中にレジスタ、逆アセンブル、任意アドレスのメモリを確認できる。
- エラーが発生した場合、利用者に原因や次の行動が分かるメッセージを表示する。
- 自動テストで主要なバックエンド動作を再現できる。

6か月後の成功:

- 専用の脆弱なテストELFで入力を与え、オーバーフローを再現できる。
- その前後でスタック表示の値・アドレス・差分を追える。
- GUIの表示が実際にGDBから取得した情報に基づき、推測した内容を事実のように示さない。
- 別の利用者やセッションのプロセス・データに誤ってアクセスしない。

## 8. 運用前提

初期版は個人的な知り合いを中心に試用する想定。ただし、対象ELFは実行されるプログラムであり、信頼できるとは限らない。公開サービス向けの大規模な隔離を初期版で先行実装する必要はないが、ローカルへのバインド、セッション分離、ファイル管理、シェル経由の危険な実行を避けるなど、基本的な安全設計は維持する。
