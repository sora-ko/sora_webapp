# 開発環境・AI開発プロセス

## 1. 開発の基本姿勢

本プロジェクトはAI支援のバイブコーディングを中心に進める。ただし、AIの生成物を自動的に正しいと見なさず、文書・自動テスト・小規模な技術検証を使って継続的に検証する。

## 2. 初期の環境候補

- OS: Ubuntu / WSL2上のUbuntuを主対象とする
- 対象: x86-64 Linux ELF
- Debugger: GDB/MI
- Optional: pwndbg
- Backend候補: Python + FastAPI
- Frontend候補: React + TypeScript
- Version control: Git

Backend/Frontendの具体的なフレームワークは推奨候補であり、ユーザー承認と技術検証を経て決定する。

## 3. 最初に作る開発基盤

1. Gitリポジトリと標準的なディレクトリ構造を用意する。
2. バージョン管理対象と生成物を区別した `.gitignore` を作る。
3. READMEにUbuntu / WSLの環境構築・起動手順を記載する。
4. Python等の依存関係をロックまたは再現可能な形で管理する。
5. フォーマッター、型チェック、静的解析、ユニットテストのコマンドを統一する。
6. CIでインストール・静的検査・ユニットテストを実行する。
7. GDB/MIを使った統合テスト用の小さなCサンプルを用意する。
8. AIに作業を依頼するときは、変更対象、完了条件、実行すべきテストを明示する。

## 4. テスト階層

### Unit tests

- API入力検証
- セッション状態遷移
- GDB/MI応答のパーサー
- アドレス・バイト列の変換
- スタック行の整形・差分計算
- エラー形式

### Integration tests

- 実際のGDBを起動してテストELFをロードする
- ブレークポイントで停止する
- レジスタと逆アセンブルを取得する
- 指定アドレスのメモリを読む
- ステップ実行後に状態が変化する
- 標準入力・出力・エラー出力を別々に扱える
- セッション終了時に子プロセスが残らない

### End-to-end tests

- ブラウザからセッションを開始する
- 実行制御を行う
- 停止状態がGUIに反映される
- メモリやスタックの表示を確認する

E2Eは最初から大量に用意せず、代表的な成功経路を少数作る。壊れやすいタイミング依存テストより、バックエンドの統合テストを重視する。

## 5. 最初に行うべき技術検証（Spike）

実装の前に、短い実験コードで次を確認する。

1. GDB/MIから対象ELFをロード・起動・停止できる。
2. GDB/MIの応答と非同期停止通知を安定して解析できる。
3. 対象プロセスの入力・出力をGDB制御用の入出力と分離できる。
4. `read()`、`scanf()`、TTYを前提とするプログラムなど、入力方式の違いをどこまでサポートするか確認できる。
5. WSLでバックエンドを動かし、Windows側ブラウザからlocalhost経由で利用できるか確認する。
6. アップロード方式の実装量と、WSL側の作業ディレクトリ指定方式の実装量を比較する。

各Spikeは、結果、再現手順、得られた結論、未解決事項を `docs/experiments/` に記録する。Spikeのコードを本番モジュールへ無条件にコピーしない。

## 6. AIに渡す作業依頼テンプレート

```text
目的:
- 何を実現するか

関連文書:
- docs/REQUIREMENTS.md の FR-xxx
- docs/ARCHITECTURE.md の対象コンポーネント

今回の範囲:
- 変更すること
- 変更しないこと

受け入れ条件:
- 再現可能な期待動作を列挙

制約:
- 互換性、安全性、依存ライブラリ等

テスト:
- 実行するコマンド
- 必要な統合テスト

文書更新:
- 更新が必要な文書

完了報告:
- 変更、テスト結果、未確認事項を報告する
```

## 7. Gitの扱い

- 1つの変更セットは原則として1つの目的に集中させる。
- 大きな機能を一度に生成させず、まず契約やテスト、次に実装、次に統合の順に分割する。
- 動作確認前に成功を前提としたコミットメッセージや報告を作らない。
- 生成物、アップロードELF、ユーザーの実データ、秘密情報は原則としてリポジトリに含めない。
